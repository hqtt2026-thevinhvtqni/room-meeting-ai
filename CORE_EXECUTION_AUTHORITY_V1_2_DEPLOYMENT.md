# Core Execution Authority V1.2 — Deployment & PC Handoff

## 1. Implemented source path

The approved architecture is:

1. Core HTTP service — room_hop_mcp.core_http_main
2. Enrolled WEE/MCP service identity — ROOM_HOP_EXECUTION_SERVICE_CREDENTIAL
3. W13 HTTP boundary — 13/EXECUTION-HOST-INFRASTRUCTURE/04_CODE/execution_host/server.py
4. Canonical W12 process provider — 12/WORK-EXECUTION-ENVIRONMENT/04_CODE/wee/bridge/real_host.py
5. Work-scoped source snapshot, execution evidence and Core append-only run record.

Do not launch the repository-root execution_host.server as a second W13 runtime. The canonical Work13 server delegates to W12's RealExecutionHost through W12ExecutionAdapter.

## 2. Core HTTP service

Run the additive Core entrypoint with:

    python -m room_hop_mcp.core_http_main

Defaults: 127.0.0.1:8000. It mounts the existing Meeting API and execution authority routes in one app. If authority config is absent or invalid, execution routes return 503; Meeting routes remain available.

**Important:** the new entrypoint is committed on the implementation branch but has not yet been wired into the user's existing start-dev.ps1 / currently running Core PID. Do not start a second process on port 8000. PC handoff must identify the actual Core launcher and integrate this app into that process, or deliberately replace it under the user's service manager.

## 3. Core environment configuration

Required:

- ROOM_HOP_EXECUTION_IDENTITIES_JSON: JSON mapping enrolled service identity IDs to SHA-256 digests of high-entropy credentials. Example shape: {"mcp-8020":"<64-lowercase-hex-sha256>"}. Store only the digest in Core.
- ROOM_HOP_EXECUTION_WORKS_JSON: JSON mapping canonical IDs such as W28 to policy objects containing work_name, allowed_identities, workspace_root, execution_workspace, evidence_root, and source_sha256. allowed_purposes defaults to ["pytest_run"].
- ROOM_HOP_EXECUTION_STORE_PATH: absolute path to persistent storage for the append-only, fsynced, hash-chained JSONL event journal.

Core runtime options:

- ROOM_HOP_CORE_BIND (default 127.0.0.1)
- ROOM_HOP_CORE_PORT (default 8000)
- ROOM_HOP_MEETINGS_DIR (optional)

The source hash must be generated by execution_host.source_snapshot.workspace_source_sha256 from the exact immutable Work execution workspace. It is a SHA-256 over sorted relative paths and file contents, not a Git commit SHA. The helper excludes .git, virtual environments, caches, node_modules, dist, and build.

For a Work directory that contains its own evidence folder, configure evidence_root as a sibling of execution_workspace under the same workspace_root, so generated evidence does not change the source snapshot on the next run. The W12 path guard requires both locations to remain beneath workspace_root.

## 4. Service identity secret

Generate the raw high-entropy service credential locally and keep it only in the enrolled MCP/WEE service process secret store. Core receives only its SHA-256 digest. The MCP/WEE service sends the raw credential in X-ROOM-HOP-SERVICE-CREDENTIAL over TLS/private transport.

Never commit or paste the raw credential into chat, GitHub files, issue comments, logs, or evidence.

The Core grant endpoint returns the short-lived grant_token once. WEE keeps it in memory and forwards it in Authorization: Bearer ... to W13. The token is not stored in the append-only journal.

## 5. Canonical W13 / W12 Host

Run the W13 module from its Work13 code directory with the Work12 source path available:

- ROOM_HOP_CORE_AUTHORITY_URL: private Core base URL; HTTPS required except loopback development.
- ROOM_HOP_EXECUTION_HOST_BIND: private interface; default 127.0.0.1.
- ROOM_HOP_EXECUTION_HOST_PORT: default 8031.

The W13 server accepts only the exact grant-bound request shape (work_id, grant_id, purpose, execution_request). It rejects caller-supplied work_context and authorized. It calls Core online before execution, obtains canonical Work paths and source hash from Core, verifies the workspace snapshot, then constructs the internal W12 context.

This implementation currently permits only pytest_run, with a single pytest command and a 30-second W12 execution timeout. W12 now:
- refuses process execution when allow_processes is false;
- passes only a small environment allowlist to the child process, not arbitrary API credentials;
- enforces a bounded timeout;
- tracks descendant processes with psutil, terminates observed descendants, and reports whether cleanup was verified;
- writes stdout/stderr and a FINAL_RESULT.json under the Work evidence root.

If process-tree cleanup cannot be verified, the result is BLOCKED rather than PASS. If Core run-recording fails after execution, W13 downgrades the result and updates the local final evidence to BLOCKED.

## 6. Routes

- POST /works/{work_id}/execution-grants — service credential; creates a short-lived Work/purpose grant and returns the token once.
- GET /works/{work_id}/execution-grants/{grant_id} — service identity status query; returns active/expired/revoked.
- GET /works/{work_id}/execution-grants/{grant_id}/validate — bearer-token validation for W13; returns canonical Work binding only while active.
- POST /works/{work_id}/execution-grants/{grant_id}/runs — revalidates the bearer token and appends a run record.
- POST /works/{work_id}/execution-grants/{grant_id}/revoke — revokes an active grant.

## 7. GitHub verification and remaining gates

GitHub Actions targeted tests currently cover Core authority, Core HTTP fail-closed mount, W12 safe/bounded execution, W13 grant bridge, and a W13→W12 real pytest execution with a Core run-record callback. The branch must be rechecked after its latest commit before opening the PR.

3. Configure the persistent Core journal path and one canonical Work policy with the exact workspace source hash.
4. Deploy the exact W12/W13 branch source to the PC/cloud runtime and restart through the approved service manager.
5. Confirm PID, resolved execution_host.server.__file__, source hashes, runtime build hash, Core URL reachability and private bind address.
6. Run live positive and negative HTTP probes: missing/invalid service credential, wrong Work, wrong purpose, expired/revoked token, wrong bearer token, source hash mismatch, timeout above grant, non-pytest command, Core outage, and Core run-record failure.
7. Verify the append-only journal survives Core restart and verify Sandbox/GitHub branch/commit readback against the exact source snapshot.

No production credential, Work source hash, store path, cloud endpoint, or deployment status is fabricated here. Until the PC/deployment gates are verified, the overall Core→W12/W13→Sandbox→GitHub E2E status remains NOT PASS.
